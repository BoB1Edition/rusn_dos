# TODO: Переход на модульную архитектуру (Crate-based)

## Цель
Разделить монолитный `dos_core` на независимые крейты, чтобы обеспечить:
- **Заменяемость CPU**: возможность подключить x86, NES (6502), JVM, Sega (Z80) и другие процессоры
- **Повторное использование**: общие компоненты (шина, память, устройства) могут использоваться разными эмуляторами
- **Тестируемость**: каждый модуль тестируется изолированно перед интеграцией
- **Безопасный переход**: старый код продолжает работать пока новый не будет полностью проверен

## Критерии приемки для каждого опкода/модуля

Перед тем как считать опкод/модуль перенесенным и удалять его из старого кода, необходимо:

1. **Unit-тесты**: Написаны тесты для всех вариантов использования (разные режимы адресации, граничные значения, флаги)
2. **Integration-тесты**: Опкод работает корректно в контексте полной системы (с памятью, устройствами, прерываниями)
3. **Сравнение поведения**: Новый код дает идентичные результаты со старым кодом на тех же входных данных (регистры, память, флаги)
4. **Тестирование на реальном коде**: Опкод успешно выполняется в реальных DOS программах (.COM/.EXE)
5. **Документация**: Добавлены комментарии о реализации, известных ограничениях, ссылках на спецификацию Intel
6. **Code review**: Код проверен другим разработчиком (если команда > 1 человека)

## Риски и стратегии смягчения

| Риск | Вероятность | Влияние | Стратегия смягчения |
|------|-------------|---------|---------------------|
| Ошибки в переносе опкодов | Средняя | Высокое | Двойное выполнение, сравнение результатов, extensive тестирование |
| Потеря производительности | Низкая | Среднее | Профилирование на каждом этапе, оптимизация горячих путей |
| Несовместимость с реальными программами | Средняя | Высокое | Тестирование на большом наборе DOS программ, bug tracking |
| Затягивание перехода | Высокая | Среднее | Четкие вехи, приоритизация по частоте использования опкодов |
| Потеря мотивации | Средняя | Высокое | Демонстрация прогресса, запуск реальных программ после каждой фазы |
