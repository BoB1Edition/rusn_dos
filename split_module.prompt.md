# Prompt: Разбивка файла на модули

## Контекст
Нужно разбить большой файл на несколько логических модулей в отдельном каталоге.

## Входные данные

- {имя_файла} — путь к исходному файлу, который нужно разбить

## Шаги

### 1. Анализ файла

- Прочитай полное содержимое файла
- Определи логические группы: функции, структуры, трейты, impl-блоки, константы, тесты
- Оцени, как лучше разбить: по функциональности, типу данных, назначению

### 2. Создание структуры

1. Создай каталог рядом с файлом, названный по базовому имени файла (если файл `foo.rs`, каталог будет `foo/`)
2. Перенеси исходный файл в каталог как `mod.rs` (через `git mv`)
   - `git mv {имя_файла} {каталог}/mod.rs`
3. В корневом `mod.rs` (или `lib.rs`), где был `mod {имя};`, замени на `mod {каталог};` — если модуль был объявлен как `mod foo;` и стал `mod foo;` с `foo/mod.rs`, то имя остаётся тем же, менять ничего не нужно
4. Разбей `mod.rs` на несколько файлов:
   - Создай в каталоге файлы по логическим группам (например: `parse.rs`, `serialize.rs`, `types.rs`, `handlers.rs` и т.д.)
   - Каждый файл импортируется через `pub mod ...;` в `mod.rs`
   - Функции из соседних модулей доступны через общий `use crate::...`
   - `pub use` в `mod.rs` для реэкспорта, если нужно сохранить старый API

### 3. Настройка видимости и pub

Для всех новых файлов (и `mod.rs` после разбивки):

- **Константы/статики**: `const` (без pub), если используется только в одном модуле; `pub(crate)` если в нескольких крейта
- **Структуры и их поля**: `pub(crate)` или без pub; поля делай `pub(crate)` только если читаются напрямую, иначе — приватные + методы-аксессоры
- **Методы**: `pub(crate)` или без pub. Публичными (`pub`) оставляй только те, что реально вызываются извне крейта
- **Трейты**: старайся `pub(crate)`; полностью публичный трейт — только если реализуется или используется снаружи
- **Функции**: без pub если только внутренняя, `pub(crate)` если используется в других модулях крейта
- **Модули** (`mod xxx`): в `mod.rs` родительского каталога — `mod` без pub или `pub mod` только если нужно извне

Проверяй каждое изменение сборкой — если что-то ломается с `not found`, делай `pub(crate)` или корректируй импорты.

### 4. Порядок в mod.rs

```rust
pub mod group1;
pub mod group2;
pub mod group3;
// ...
pub mod groupN;

// Реэкспорт только если нужен обратно-совместимый API:
// pub use group1::SomeType;
// pub use group2::some_function;
```

### 5. Проверка

```bash
cargo build
cargo clippy
cargo test
```

Убедись, что линтер и тесты проходят. Если clippy выдаёт предупреждения — исправь их. Не оставляй неиспользуемые импорты и мёртвый код.

## Замечания

- Не дублируй код — используй `pub use` для реэкспорта
- `use crate::...` пути могут сломаться, если глубина изменилась; проверяй импорты
- `git mv` сохраняет историю файла
- Тесты остаются рабочими — если тесты используют приватные функции, добавь `#[cfg(test)] pub(crate) use ...` в `mod.rs`
