# SKILL.md — Описание навыков для эмулятора rusn_dos

## Навыки разработчика

### 1. Разработка инструкций x86

Понимание архитектуры x86 (real mode, partial protected mode):
- ModRM (16/32-bit, SIB, segment defaults)
- Префиксы (0x66 operand size, 0x67 address size, 0xF2/F3 REP, 0xF0 LOCK, segment overrides)
- Вычисление флагов (CF, PF, AF, ZF, SF, OF) для арифметических, логических и сдвиговых операций
- Двухбайтовые опкоды 0x0F
- Планарные видео-режимы VGA (sequencer, graphics controller, CRTC, attribute controller, DAC палитра)
- Разбивка крупных файлов инструкций на подкаталоги с модулями (`alu/`, `mov/`)

### 2. Разработка DOS API

- INT 21h функции (AH=00h-6Ch): файловые операции, управление памятью (MCB), DTA, ввод/вывод, EXEC (AH=4Bh/4Dh)
- INT 2Fh мультиплексные прерывания (DPMI, Windows)
- INT 33h — break check (получить/установить), boot drive, версия DOS
- Механизм suspend/resume для неблокирующего ввода с клавиатуры
- INT 10h функции (AH=00h-0Fh, 12h): видеорежимы, курсор, скроллинг, вывод символов

### 3. Разработка BAT-интерпретатора

- BAT-файлы уровня COMMAND.COM: `crate/dos/src/bat/runner.rs`
- Каждая дочерняя программа — свежий `DosSystem` через `loader::load_executable()`, состояние оболочки (`ShellState`: CWD, диск, окружение, errorlevel, echo) живёт в Rust
- Встроенные команды: echo, cd, cls, goto, if errorlevel/exist, set, pause, call, exit, rem, смена диска
- Раскрытие `%0`–`%9`, `%VAR%`, `%%`→`%`; кавычки в токенах сохраняются
- `--max-call-depth` (1..=255) ограничивает вложенность BAT; `if_depth > 4` запрещён; CALL :label не поддержан (Этап 4)
- Дисплей передаётся по значению `Option<&mut dyn Display>` из `src/app.rs`, чтобы заимствование окна не переживало один вызов (`child_loop()`)

### 4. Разработка периферии

- Трейт Peripheral: port_read/write, mem_read/write, tick
- Трейт Display: update, poll_keys, pump_events (поддержание окна при suspend)
- Интеграция с Motherboard: регистрация портов, MMIO, вызов tick()

### 5. Добавление новой эмулируемой системы

- Новый крейт в `crate/`, зависимость от `bus` + `log`
- Реализация `Cpu` trait или предоставление `step()`
- Загрузка ROM/образов через `load_rom()` / `load_cd_image()`
- Интеграция с `DosSystem` или как standalone

### 6. Отладка

- `RUST_LOG=debug/trace` для логирования
- `X86Cpu::new_with_tracer("logopcode.txt")` для трассировки опкодов
- `--no-log` для отключения трассировки
- `-w C:\\<dir>` для установки DOS-рабочей директории (в test.sh используется для biing/XCOM/TASM)
- `-d N` (--max-call-depth) для проверки рекурсивных .BAT

### 7. Документирование/Документация

- Основной язык русский
- Основные документы пишутся на русском и английском языке
- Документация должна быть полной, включая указания почему именно так реализовано, как можно переделать при необходимости, примеры использования, какие тесты проводятся.
- При обновлении функционала: синхронно обновлять `AGENTS.md`, `CHANGELOG.md`, `DESIGN.md`, `ERRORS.md`, `GOALS.md`, `README.md`, `SKILL.md`, `TODO.md`, `docs/*`
- Проектная память: `MEMORIES.md` — ключевые решения, договорённости и хронология для быстрого воссоздания контекста агентами

## Типичные задачи

### Добавление нового опкода x86
1. Создать функцию в соответствующем файле `crate/x86/src/instructions/` (при большом размере — разбить на подкаталог: `alu/`, `mov/`)
2. Добавить вызов в `executor.rs` (execute или execute_0f)
3. Написать тест в `crate/x86/tests/`
4. Обновить `docs/x86.md`

### Добавление новой функции DOS API
1. Добавить обработку в `crate/dos/src/interrupts/dos/` (в соответствующий модуль `console.rs`, `file_ops.rs`, `dir.rs`, `find.rs`, `memory.rs`, `exec.rs`, `misc.rs`) или `bios.rs`/`ems.rs`
2. Добавить в dispatch `interrupts/dos/dispatch.rs`, вектор в `interrupts/mod.rs` если новый вектор
3. Обновить `docs/dos-api.md` и `README.md`

### Добавление периферии
1. Создать файл в `crate/bus/src/peripherals/` (или подкаталог для сложных устройств, например `video/`)
2. Реализовать `Peripheral` trait
3. Добавить в Motherboard: поле, инициализацию, проброс портов
4. Вызывать `tick()` в step_frame если нужно

### Добавление новой BAT-команды
1. Добавить ветку в `Runner::exec_line()` в `crate/dos/src/bat/runner.rs` (встроенные) или `Runner::run_command()` (внешние)
2. Внешнюю команду не забыть в `resolve_command()` (поиск COM/EXE/BAT)
3. Обновить TODO.md и CHANGELOG.md

### Добавление EXEC-поддержки (дочерние процессы внутри DOS)
1. Функция в `crate/dos/src/interrupts/dos/exec.rs` парсит параметрический блок ES:BX → `ExecRequest`
2. `step_frame()` ловит `exec_request` → `start_child()` (снимок `ParentSnapshot`, загрузка ребёнка)
3. По завершении ребёнка — `finish_child()` (восстановление родителя, AX/CF, `child_exit_code`)
4. Код возврата — INT 21h/AH=4Dh (`get_return_code`)

### Разбивка крупного файла на модули (рефакторинг)
1. Создать подкаталог с `mod.rs`, который реэкспортирует публичные функции
2. Разнести логику по файлам: группировать по функциональности
3. Все публичные функции оставить доступными через `pub use` в `mod.rs`
4. Импорты в `executor.rs`/других файлах обновить на новый путь
5. Обновить `docs/architecture.md`, если меняется структура крейта

### Добавление документации
1. Создать файл в `docs`
2. Описать документируемый функционал

### Подготовить крейт/модуль к альфе
1. Просмотреть весь крейт/модуль
2. Проверить нужно ли его переводить на асинхронный/мультипоточный режим
   a. Если необходимо: создать план по переводу, задать необходимые вопросы в случае спорных моментов или не понимания вектора развития приложения, согласовать план, реализовать план, убедиться в отсутствии ошибок.
   б. Если нет необходимости: Сообщить об этом.
   в. Если есть сомнения задать вопрос, описав положительные и отрицательные моменты реализации. При выборе о том что необходимо смотреть пункт а.
3. Создать под него документацию
4. Создать все необходимые комментарии в коде
5. Провести все необходимые тесты
6. Проверить код
7. Создать план перехода: для модулей mod_{имя_модуля}.alfa.md, для крейта crate_{имя_модуля}.alfa.md
8. Согласно плану перевести крейт
9. Изменить файлы ALFA.md, PREALFA.md и BETA.md

### Предложить крейт/модуль к альфе
1. Изучить код крейтов и модулей
2. Выбрать те которые достойны перевода (полностью дописаны по функционалу, скорее всего не будут больше меняться и нет останавливающих факторов)
3. Проверить нужно ли его переводить на асинхронный/мультипоточный режим
   a. Если необходимо: создать план по переводу, задать необходимые вопросы в случае спорных моментов или не понимания вектора развития приложения, согласовать план, реализовать план, убедиться в отсутствии ошибок.
   б. Если нет необходимости: Сообщить об этом.
   в. Если есть сомнения задать вопрос, описав положительные и отрицательные моменты реализации. При выборе о том что необходимо смотреть пункт а.
4. Подготовиться к созданию документации под модуль/крейт
5. Подготовить все необходимые тесты
6. Проверить код
7. Создать файлы с описанием почему уже можно и желательно перевести его в alfa: для модулей mod_{имя_модуля}.prealfa.md, для крейта crate_{имя_модуля}.prealfa.md, в них описать плюсы и минусы перевода.
8. Изменить PREALFA.md

### Найти ошибки
1. Проанализировать кодовую базу
2. Найти дублирующий код
3. Найти мертвый код
4. Найти непоследовательный код
5. Найти синтаксические ошибки кода
6. Найти ошибки реализации функций
7. Найти логические ошибки
8. Найти слишком "открытый" код (код в котором pub можно заменить на pub(crate) или вообще убрать pub)
9. Найти частично реализованные методы (методы в коде которых явно указано, что работаем только с памятью, а регистры оставляем на потом и подобное)
10. Найти небезопасный код
11. Проверить все тесты, выявить ошибки в них и на них
12. Внести всё в файл ERRORS.md

```bash
cargo build                               # Сборка

cargo test -p x86                         # Тесты CPU
cargo run Run test/test2 --graphics       # Запуск DOS-программы
cargo run Run test/build.bat --graphics   # Запуск BAT-файла
cargo run Run app/XCOM/GO.COM --graphics -w C:\\XCOM
./test.sh                                 # Полный прогон целевых программ
```
